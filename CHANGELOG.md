# Changelog

## Unreleased

- Assembly code can live in several banks: `build.assembly.banks` lists extended RAM banks (1-31) and the ld65 MEMORY area holding each one's code. Each area, linked at `$8000-$BFFF` with its own output file (`file = "%O.bank1"`) and `bank = n` (which ca65's `.bank()` reads), becomes its own PRG (`build/code.bank1.prg`, `CODE.BANK1.PRG` on the card), and the loader puts it in its bank with `BANK 1:BLOAD "CODE.BANK1.PRG"` before the main image, in `BOOT.BAS` and debug launches alike. The build reports an area that is missing, shares the main output, says another bank or reaches past `$BFFF`. New `AssemblyBuildRequest.banks`, `AssemblyBuildResult.banks` and `segmentBanks`, `createAssemblySourceMap(debug, {segmentBanks})` and `readLinkerMemory` in `@clementina/assembler`. Breakpoints in banked code stop in their own bank.
- The assembly language server warns about a store to `VIA_ORA` (or `VIA_ORA_NH`, a mirror, or a macro that does one) in a segment linked at `$8000-$BFFF`, which switches the bank under the running code; a store right after `lda #n` of the code's own bank is not reported. New `@clementina/asm-lsp` exports `bankedSegments`, `bankSwitchWarnings`, `workspaceBankWarnings` and `isBankSelect`.
- New launch attribute `stopOnBankSwitch` (and `createProjectDebugSession` option): the debugger stops just before banked code stores to `VIA_ORA`, with "Bank switch" as the reason. New `bankSwitchStops` in `@clementina/debug`.
- Add `examples/multi-bank`: a BASIC program shows rooms whose code is in banks 1 and 2, through a far-call routine at `$7000` that switches banks; bank 2's room calls bank 1's frame.
- `saveProject`, and so Studio, keeps `clementina.yaml` as you wrote it: only values that changed are rewritten, so comments, key order and hex addresses stay, and an unchanged manifest is written back byte for byte. Addresses it writes new are `$` hex (`$7000`, `$14000`), not decimal. New `manifestText(manifest, previousText?)` in `@clementina/project`.
- `target.phi2Hz` sets the speed the program runs at, from 1 Hz to 8 MHz; validation no longer rejects speeds other than 1.2 MHz. The generated loader (`BOOT.BAS`, `build/boot.cbas` and direct launches) starts with a new `speed` load step, two lines of POKEs to MIA's `CFG_SPEED_L/M/H`, so the program runs at that speed on the board and in the emulator. A real-time debug session starts the emulator at it; the `clementina.debug.speed` setting is now empty by default and overrides it only when set. New `SpeedStep` load-step type. In `boot.cbas` and `BOOT.BAS` the speed and `memoryTop` steps follow a `REM SET CPU SPEED` or `REM MOVE BASIC MEMORY TOP` line.
- The VS Code extension understands ld65 linker configurations: `link.cfg` (and any `.cfg` a project names in `build.assembly.linkerConfig`) opens as **ld65 Linker Configuration** with highlighting, and `@clementina/asm-lsp` serves it. As you type it checks ld65's rules (blocks and their order, attributes and their values, required attributes, names defined twice, unknown memory areas, expressions) and then runs ld65 itself on the unsaved text (with no object files, so nothing is written), and warns where a memory area takes memory the kernel, the stack or, for a project with a BASIC program, BASIC uses ($00-$97, the input buffer, $1600 up to `build.basic.memoryTop`), sits on I/O or MIA, overlaps another area, does not start at `build.assembly.loadAddress`, or where the sources use a segment SEGMENTS does not place. Hover explains blocks, attributes, memory areas (range, size, segments, the Clementina memory they cover), segments (where they load and the source lines that use them) and addresses; completion offers blocks, names, attributes and values, including the free places in Clementina's memory for `start`; go to definition, the outline and folding work too. New setting `clementina.assembly.ld65Path`; `clementina.assembly.diagnostics` also controls ld65. New `@clementina/asm-lsp` exports `parseConfig`, `configDiagnostics`, `configHover`, `configCompletions`, `configDefinition`, `configOutline`, `checkWithLd65`, `findLd65`, `findTool`, `clementinaMemoryMap` and `manifestAddress`.
- Debugging in VS Code runs the game in real time: `F5` builds the project, starts `clementina-emulator --headless --control` (1.2 MHz by default) and opens `clementina-video-client`, where you play while breakpoints stop it in the editor. The status bar shows the speed; click it, or run **Clementina: Set Emulator Speed…**, for 1, 1.2, 2, 4 or 8 MHz or unthrottled. Restart resets and starts the project again. New launch attributes `realtime`, `speed` and `videoClient`, and settings `clementina.debug.speed`, `openVideoClient`, `emulatorPath` and `videoClientPath`. `F5` works without a `launch.json`. Needs a clementina-6502 with `--headless`.
- Projects with BASIC and assembly, like every `clementina new` project, debug both at once (new `ClementinaProjectDebugSession`): breakpoints in `.cbas` and `.s` files stop, the call stack ends with the BASIC line that called the routine, and stepping past the routine's `RTS` stops at the next BASIC statement. BASIC breakpoints set from VS Code now verify (the session matched only absolute paths).
- BASIC breakpoints stop before the line runs. The ROM's `NEWSTT2` hook fired after a statement, with `CURLIN` still on that line, so a stop "on" a line came after it ran; the debugger now uses NEWSTT's new-line point (`basicRuntimeDebug.lineStartAddress`, $1EB9). A line with several statements stops once, and a step runs the whole line.
- Assembly frames, breakpoints and disassembly lines open in VS Code: the adapter resolves the debug info's project-relative paths (`src/hello.s`) against the project folder (it showed "Could not load source").
- Hover and watch evaluate registers (`A`, `X`, `Y`, `SP`, `P`, `PC`) and assembly symbols: a label shows its address and bytes, a constant such as `KERN_CHROUT` its value. The hovered file picks the language, so `A` is the register in `.s` and the variable in `.cbas`. New `AssemblySymbols`, `DebugEvaluation` and the `symbols` session option. The Registers view shows `P` as hex, flag letters and binary (`$83 Nv-bdiZC %10000011`, uppercase = set); new `formatStatusRegister`.
- BASIC line breakpoints filter the ROM statement hook in the emulator when it supports `setBreakpointFilter`, so a game runs at full speed between the lines you stop on. New `EmulatorClient` methods `speed`, `setSpeed`, `setBreakpointFilter` and `clearBreakpointFilter`.
- Emulator tools are found in `~/.clementina/bin` (or `$CLEMENTINA_HOME/bin`) before `PATH` (new `findInstalledTool`), so an editor started from the Dock finds them. `startEmulatorProcess` takes `realtime` to start the real-time emulator, and `createProjectDebugSession` passes it through and returns `client`.
- The VS Code extension helps edit `clementina.yaml`: it registers the project schema with Red Hat's YAML extension (now an extension dependency) for field completion, hover and schema errors, and every field of `project.schema.json` has a `description`. It also shows the SDK's own project checks as you type (missing files, asset errors, unknown IDs, slots, banks, hex addresses out of range) and completes project files in path fields. New in `@clementina/project/node`: `checkManifestText`, `manifestPathFieldAt`, `manifestPathCandidates`, and `loadProject(root, {manifestText})`.
- The generated loader (`build/boot.cbas`, `BOOT.BAS` and direct launches) writes addresses in hex: `POKE $3F,$00:POKE $40,$70:CLEAR`, `MIALOAD "PALETTE.BIN",$00100`, `BRUN "GAME.PRG",$8010`. A `MIALOAD` line has up to three characters less room for its path within the editor's 80. The starter, Catch the Star and the docs write BASIC addresses in hex too (`SYS $7000`, `PEEK($0281)`).
- Manifest addresses and sizes (`build.assembly.loadAddress`, `build.basic.memoryTop`, and a `build.assets` slot's `mia`, `address` and `size`) take hex as well as numbers: `$7000` or `0x7000`, unquoted. The checked manifest holds numbers; a malformed one gets `project.address`, and an out-of-range one is reported in hex. The starter and Catch the Star write `$7000`. `ClementinaProjectManifest<ManifestAddress>` types the manifest as written.
- The `clementina new` starter is minimal: `src/main.cbas` prints a line, calls the assembly routine `hello` (`src/hello.s`, which prints a line through the kernel) with `SYS $7000` and waits for a key, and `checks/smoke.json` is its one check. It replaces the press-A starter game (`src/score.s`, `add_point`, `checks/code.json`).
- Add `examples/catch-the-star`, a complete game that the books' "Your first project" builds from the starter: BASIC owns the rules (score, lives, star speed, where stars start, game over and high score), and the assembly routine `play` runs the game 60 frames a second with the library's `WaitTick` and `ReadPad`: the arrows, the basket and the falling stars. SDK CI's new `examples` job builds the emulator automation from clementina-6502 and runs `clementina check` on it and on a new starter.
- Every build writes the card folder `build/sd` (`sdRoot` is never the project folder any more), holding a tokenized `BOOT.BAS`, the program (`GAME.BAS`, `CODE.PRG`), its palette and CHR files and any assets; load-plan paths are relative to it. `RUN "BOOT.BAS"` starts any project: for a BASIC program, `BOOT.BAS` ends with `RUN "GAME.BAS"`, which needs a ROM with `RUN "path"`. The readable copy is `build/boot.cbas` (it was `bootstrap.cbas`). `clementina run`, `check` and the MCP server start projects by typing `RUN "BOOT.BAS"` (new `EmulatorClient.launchBoot()`), and `build` prints `Built the SD card in build/sd. Start it with RUN "BOOT.BAS".`
- Text BASIC source uses the `.cbas` extension, so it can't be mistaken for a tokenized `.BAS` program: the `clementina new` starter's entry is `src/main.cbas`, tokenized programs keep `.BAS`, the VS Code extension opens `.cbas` files as Clementina BASIC, and a `program.entry` without `.cbas` gets the `project.program.extension` warning.
- Add `@clementina/asm-lsp`, a language server for ca65 assembly, and run it from the VS Code extension for `.s` and `.inc` files: ca65's errors and warnings as you type (with the build's include directories and defines), hover for instructions (flags, every addressing mode with opcode, bytes and cycles, and the mode the line uses), directives, symbols (values, structure offsets, comments and, after a build, label addresses) and numbers, completion, signature help for macros, go to definition, references, highlights and rename across the workspace and the Clementina library, the outline, workspace symbols, folding and `.include` links. The settings `clementina.assembly.ca65Path` and `clementina.assembly.diagnostics` control the checks.
- The `clementina new` starter includes `.vscode/settings.json`, which opens `.s` and `.inc` files as Clementina Assembly and `.cbas` files as Clementina BASIC even when another extension, such as Go's, claims them.

## 0.3.0-alpha.4

Fourth alpha. `clementina new` starts every project from one starter, `clementina update` updates the CLI and the installed tools, and `clementina dev` switches every terminal to local dev builds. Tested with clementina-6502 v0.4.0-alpha.1, clementina-video-client v0.1.0-alpha.1, clementina-studio v0.1.0-alpha.1 and cc65 2.19 (`cc65-v2.19`).

- `clementina new <directory> [--name <name>]` creates one starter with both program parts: a BASIC program that calls an assembly routine with `SYS`, above a `build.basic.memoryTop` of `$7000`, with smoke and code checks. `--template` and the `basic`/`assembly` starters are gone, as are the `DEFAULT_TEMPLATE` and `TEMPLATE_NAMES` exports and the `template` field of `new --json`. Building the starter needs cc65.
- Add `clementina update [tool ...] [--check]`, which moves the standalone CLI and every installed tool to its newest release, or with `--check` lists the newer releases.
- The install script is the one supported install path; `docs/install.md` no longer offers npm or Homebrew installs of the CLI.
- Add `clementina dev on|off|status`, which switches every terminal between the dev builds in `~/.clementina/dev/bin` and the installed tools; the installed CLI runs the dev build of the CLI and links `bin/` to the dev tools until `dev off`. It replaces `clementina-dev.sh`, which `npm run dev:install` no longer copies.

## 0.3.0-alpha.3

- `clementina install` and the install scripts fall back to the GitHub releases feed when the GitHub API refuses an unauthenticated request (60 an hour per address), and send `GITHUB_TOKEN` when it is set.
- The cc65 packages include `asminc` and `cfg`, which ca65 needs for `.macpack`; on macOS and Linux their `bin/` commands set `CC65_HOME` themselves.

## 0.3.0-alpha.2

Second alpha. Install the SDK and its toolchain on macOS, Linux or Windows with one command (`install.sh` or `install.ps1`, see `docs/install.md`). Tested with clementina-6502 v0.4.0-alpha.1, clementina-video-client v0.1.0-alpha.1, clementina-studio v0.1.0-alpha.1 and cc65 2.19 (`cc65-v2.19`).

- Add `clementina install [tool[@version] ...]`, which downloads cc65, the emulator, the video client and Studio (their newest releases, or the versions named) into `~/.clementina`, checks them against `SHA256SUMS`, and adds them to `PATH`. `install.sh` and `install.ps1` install the newest CLI, or the one `--version` names, and run it, so one command sets up macOS, Linux or Windows (see `docs/install.md`). CLI commands also look for tools in `~/.clementina` after `PATH`.
- Build cc65 for every release platform in the `cc65` workflow; a `cc65-v<version>` tag publishes the archives `clementina install cc65` uses.
- Add `clementina mcp`, which serves the MCP server over stdio from the CLI, so the standalone executables run it without Node.js.
- Add `clementina --version`, which names a checkout build and its commit; `doctor` prints it and the path and version of each tool it finds.
- Add dev installs: `npm run dev:install` puts launchers for this checkout's `clementina` and `clementina-mcp` in `~/.clementina/dev/bin`, and `clementina-dev on|off|status` switches a shell between them and the installed tools.
- Remove `program.kind`. A project is described by its parts: an optional BASIC `program.entry` and an optional `build.assembly`, which now lists its own `sources`. With both, the load plan `BLOAD`s the PRG and then runs the BASIC program. Build results, `clementina build --json`, MCP and the debugger report `assembly`/`basic` parts instead of a kind; `create-game.mjs init` takes `--template`.
- Add `build.basic.memoryTop` and the `memoryTop` load-plan step, which lower BASIC's `MEMSIZ` so bank-0 RAM above it is free for code a BASIC program calls.
- Add `clementina new <directory> [--template basic|assembly] [--name <name>]`, which creates a project from templates embedded in the CLI, including the standalone executable. `create-game.mjs init` now uses it, and the starters' READMEs use `clementina` commands.
- Add `clementina check [directory]`, which runs a project headless and tests `checks/smoke.json` and `checks/code.json`, and `clementina debug [directory] --line <n>`, which stops at a source line and saves CPU, memory and video evidence. They replace the logic of `create-game.mjs check`, `code-game.mjs` and `debug-game.mjs`, which now call them, and work in the standalone executable.
- Every build writes `memory-layout.json`: each part's place in CPU memory and MIA RAM next to the machine's areas, with overlaps as `build.layout.overlap` warnings. Overlapping asset slots are now a warning too.
- A load plan ending in a BASIC program also renders as a numbered bootstrap, ending with its `LOAD`.
- Rename the asset runtime to the Clementina library, the SDK's general library of 6502 routines for Clementina programs, and link it into every assembly build, not only builds with `build.assets`. `@clementina/runtime` is now `@clementina/lib`; `runtime.inc` is `clementina-lib.inc`, `runtime.lib` is `clementina.lib` (built in `<outputDirectory>/lib/`), and the `RT_`/`rt_` prefix is `CL_`/`cl_` (`RT_CHECKS` is `CL_CHECKS`, `rt_error` is `cl_error`). `RuntimeSave`/`RuntimeRestore` are `LibSave`/`LibRestore`, the TypeScript `runtime*`/`RUNTIME_*` exports are `library*`/`LIBRARY_*`, `buildRuntime` is `buildLibrary`, and the memory report's `runtimeCode` is `libraryCode`. The `checks` option moves from `build.assets` to `build.assembly`. There are no compatibility aliases. The assembly starter's linker configuration now has the segments the library needs.
- The VS Code extension opens `.s` and `.inc` files as Clementina Assembly: a 65C02/ca65 TextMate grammar that also highlights the Clementina library's macros, routines and spec constants from the public includes (generated by `npm run generate:asm-grammar`), and gutter breakpoints for assembly and BASIC sources.
- Show why BASIC renumbering failed (an unnumbered line, a number past 63999, or a line pushed past 80 characters) instead of leaving the file unchanged without a message.
- Write glyphs and per-character string styles in portable BASIC source with `{…}` tags (`{$81}`, `{c2 fy}`): the compiler emits the ROM's style sidecar, the detokenizer writes the tags back so programs saved on the machine round-trip, and the 80-character limit counts typed characters (`sourceNotation` in `specs/basic.json`).
- Tokenize quoted `DATA` items as the ROM does, so a colon inside one no longer ends the `DATA` statement, and accept a style record for a string left open at the end of its line.
- Complete, hover and diagnose BASIC tags in the language server. In VS Code, a Clementina Screen panel shows what the lines under the cursor or selection print, laid out as the ROM's `PRINT` does; a glyph picker and a command that styles the selection help write tags.
- Record KERN_CHROUT's console control codes in `specs/kernel-abi.json` and check them, and the BASIC style sidecar's constants, against the ROM in `npm run check:drift`.

## 0.3.0-alpha.1

First alpha release. GitHub releases carry the standalone CLI executables, the VS Code extension (`.vsix`) and `SHA256SUMS`; npm packages are published under the `alpha` dist-tag.

- PRG files carry a 2-byte load-address header with no bank byte. Load plans pick each PRG bank with `BANK n:` and start the program with `BRUN`, `MIALOAD` steps no longer emit a length, and the BASIC tokenizer keeps hex digits after `$` (up to 6) raw instead of crunching `CD` or `DEF`, matching the ROM.
- Generate `clementina.inc` and `mia.inc` from `specs/` (`npm run generate:includes`) and put them on every assembly build's include path; the asset runtime uses MIA's names from them.
- Add automated package-content checks and CI for supported Node versions.
- Make the SDK npm packages publishable under GPL-3.0-only.
- Check assembler and emulator availability through `clementina doctor`.
- Add a physical hardware audio fixture and capture analysis workflow.
- Build packages through TypeScript project references (`npm run build` runs `tsc -b`; `npm run clean` removes output).
- Share `errorMessage`, `formatHex`, `isIntegerInRange`, and `SerialQueue` from `@clementina/core` instead of per-package copies.
- Export the default emulator executable and `CLEMENTINA_EMULATOR` lookup from `@clementina/emulator-client/node`.
- Raise `DebugSessionError` from BASIC debug sessions, matching assembly sessions.
- Ship the CLI as standalone executables for Linux, macOS, and Windows that need no Node.js install (`npm run build:binaries`; attached to tagged GitHub releases).
- Embed the ca65 runtime sources as `runtimeFiles` in `@clementina/runtime`; builds write them instead of copying from the package directory.
- Bundle the VS Code extension with its debug adapter and BASIC language server so the `.vsix` packages from the workspace (`npm run package` in `packages/vscode-extension`).
- Add `clementina project import` to turn a Studio session file into a new portable assembly project.
- Add `WaitTick`, `ReadPad` and `KeyHeld` to the runtime: frame timing from MIA's 60 Hz count, and held gamepad and keyboard input.
